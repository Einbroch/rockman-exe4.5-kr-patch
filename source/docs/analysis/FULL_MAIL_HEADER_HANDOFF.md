## 적용 범위

고정 셀 한 줄 한도는 원문 최장과 같은88px다. 초안에서 넘치던 네 제목은 needs_review 개발 문구로 다음처럼 조정했다.

- `또 1체 다크로이드` — 원문의 숫자1 보존, 80px
- `의문의 오퍼레이터!` — 80px
- `오퍼레이터 정체!` — 72px
- `길거리 습격 발생` — 72px

전체 최대 폭은80px다. 입력은 `analysis/full_mail_header_v1_r2/6DD63C_selected_asset.json`, 개별 축약 근거는 `translations/full_mail_header_layout_v2.json`이다. 모두 `development-draft; NON-DISTRIBUTION`, `needs_review`, `release_eligible=false`다.

## 검증 결과

- `static_verification_r3.json`: 새 헤더20개, 전체 헤더22개, 미선택 헤더20스크립트 보존, 헤더 외65개 아카이브 컴파일 내용 동일, 선언된 원본 영역 쓰기만 발생, 기존 메일 본문 raw clone 내용 동일, 기존 패키지 해시 불변 PASS.
- `cpu_verification_r3.json`: 공통 메일/키 아이템 ROM 선택기 합성 CPU867조건 PASS.
- `runtime_verification.json`: 동일 바이트 ROM에서 새 게임·초기 설정·자판3페이지·네 내비 선택·정상 첫 메일23쪽·목록 복귀·재열기 PASS. 첫 헤더 `FROM: I.P.C. / 제목: 고객 여러분께` 실제 표시 확인.
- `header_runtime_verification_r3.json`: 나머지10개 대응 발신자/제목을 현재 ROM의 실제 압축 해제 아카이브와 원래 고정 셀 목록 출력기로 격리 표시 PASS. `header_gallery`의10장/2시트를 직접 확인했으며 글자 잘림, 칸 침범, `NEW` 표식 겹침이 없다.
- 관련 단위 테스트15개와 헤더 선택 테스트7개 PASS. 최종 ROM 두 번 빌드 결과 전체 바이트 동일.

r3는 런타임 검사에 사용한 r2와 ROM 전체 바이트 및 SHA256이 같다. r3는 QA 중 보완된 감사 코드까지 현재 빌드 도구 해시에 포함하기 위해 다시 생성한 최종 기록이다.

## 증거 한계와 다음 작업

정상 수신으로 확인한 것은 첫 `I.P.C. / 고객 여러분께` 메일뿐이다. 나머지10쌍은 정상 체크포인트에서 헤더 테이블 읽기만 격리 전환한 진단 화면이다. 따라서 실제 스토리 진행에 따른 수신 조건, 저장 후 수신 목록, 후속 본문과 헤더의 자연 선택 상태, 퀘스트 연속 진행은 아직 증명하지 않았다.

별도 임무 메일 표기 아카이브 `6DD864`, 다른 내비 전용 메일, 나머지 미선택 일본어·이미지, 자동 한글 조합 입력과 저장/재표시도 남아 있다. 다음 작업은 정상 스토리 수신 상태의 writer/flag를 찾거나, 별도 임무 메일 헤더의 실제 소비 폭과 분기를 검증하는 것이다.
