# 초기 조사 — Rockman EXE 4.5 Real Operation 일본판

## 범위와 근거

- 지원 입력: `project.json`의 `rockman-exe45-jp-retail` 한 리비전.
- 원본 ROM은 해시·GBA 헤더가 모두 일치한다.
- 외부 후보 카탈로그: RockmanEXEZone의 MMBN45 영문 패치 소스 커밋
  `61c8df305f76b3b94395cf58cee16d816b56eaaa`에 포함된 `exe45.tpi`.
- 후보 카탈로그는 대상 ROM에서 전수 검증된 뒤에만 아래 결론에 사용했다.

## 확정된 구조

| 항목 | 결과 | 근거 |
|---|---:|---|
| 텍스트 아카이브 | 732 | `exe45_tpi_verification.json` |
| LZ77 아카이브 | 285/285 정상 | 같은 파일 |
| 비압축 아카이브 | 447 | 같은 파일 |
| 포인터 | 961/961 일치 | 같은 파일 |
| 포인터 주장 없는 행 | 8 | 같은 파일 |
| 무변경 왕복 페이로드 | 732/732 동일 | `exe45_nochange_roundtrip.json` |
| 왕복 중 이동 | 213개 | 같은 파일 |
| 왕복 ROM 증가 | 137,788바이트 | 같은 파일 |

TextPet의 `.tpi`는 `0x`가 붙은 수만 16진수이고, 접두사 없는 압축 크기는
10진수다. EXE3용 검증기의 기존 16진 고정 파서는 285개 압축 행을 모두 거짓
불일치로 만들었으며, `tools/verify_tpi_index.py`에서 두 표기를 구분하도록 수정했다.

무변경 왕복의 동등 기준은 압축 바이트 동일성이 아니라 게임이 소비하는 해제 후
페이로드 동일성이다. 원본과 왕복본의 1,065,382바이트가 아카이브별로 전부 같다.
다만 TextPet 기본 재압축은 213개를 이동하고 ROM을 키우므로 최종 제품 빌드는
손대지 않은 아카이브의 원본 저장 바이트를 보존해야 한다.

다음은 검증된 732개 카탈로그의 초기 집계이며 게임 전체 텍스트의 완전한 분모가
아니다. 스크립트 수와 별개로 문자열·문자 수는 초기 정규식의 삼중 따옴표 및 escape

## 재사용 경계

EXE3에서 재사용하는 것은 TPI 전수 검증, 무변경 왕복, 페이로드 동등성, 코퍼스
측정이라는 도구와 검증 원칙이다. EXE3의 주소, 폰트 뱅크, 코드페이지 확장 패치,
VRAM 배치 및 렌더러 수는 4.5에 적용하지 않는다. 영문 4.5 패치의 주소·폰트·ASM도
후보 근거이며 대상 ROM 및 실제 소비자에서 독립 확인하기 전에는 제품 사양이 아니다.

### 폰트 후보의 정적 경계

공개 영문 패치의 재배치 파일 맵에서 세 범위를 후보로 가져와 대상 ROM 자체에서
범위 해시, 레코드 수, 팔레트 니블 및 정렬 리터럴 참조를 측정했다. 결과는
`exe45_font_candidates.json`에 있으며 아직 렌더러 의미를 확정하지 않는다.

| 후보 | ROM 범위 | 가정 레코드 | 개수 | 상태 |
|---|---|---:|---:|---|
| big | `0x601738..0x607F38` | 64바이트 | 416 | 후보 |
| variable | `0x608758..0x612CB8` | 96바이트 | 441 | 후보 |
| mono | `0x619EF8..0x620EF8` | 64바이트 | 448 | 후보 |

문자표와 일반 가변폭 후보는 정적으로 맞물린다. `00..E3`은 인덱스
0..227, `E4 xx`는 228+xx이며, 문자표는 441칸 중 `0x81` 하나를 제외한 440칸을
지정한다. `0x608758`의 후보는 정확히 441×96바이트다. 폭 표 후보 두 벌은 각 441개의
32비트 값을 가지며 `0x5290C`는 공백만 8픽셀/나머지 11픽셀,
`0x52FF0`은 전부 11픽셀이다. 이 구조는 실제 화면에서도 확인됐다. 임시 코드 치환
빌드는 메가맨 첫 소개문에 `한글`을 표시했고 레코드 129/132를 읽었다. 이어 전체
11,172자를 붙인 확장 빌드는 `F9 FC + U+AC00 기준 16비트 음절 번호`로 같은 문구를
표시하고 레코드 11030(`한`)/954(`글`)를 읽었다. 콜드 부팅 후 일반 패드 입력만
사용했으며 안정 캡처 10장에서 인접 일본어와 메시지 진행도 유지됐다. 근거:
`exe45_codepage_and_font_structure.json`, `exe45_visibility_poc_runtime.json`,
`exe45_extended_dialogue_poc_runtime.json`.

현 시점 판정은 **일반 대사 한글화 경로 채택 가능, 전체 게임은 조건부 진행**이다.
일반 대사 글꼴·폭·확장 디스패치는 실행으로 확인됐다. 검증된 732개 아카이브의
해제 페이로드 1,065,382바이트에는 기존 `F9 FC`가 0건이므로 이 모집단 안의 충돌은
없다(`exe45_f9fc_collision_scan.json`). TextPet 역해석은 후속 v3 검사에서
연속·문장 시작·명령 직후 한글 11,172자+쉼표 및 원본 732개 아카이브를 통과했다
(`exe45_korean_codec_roundtrip_v3.json`). 소개 4개+PET 확인 45개+록맨 저장 16개
단위의 보호된 번역·재삽입이 가능하다. 첫 만남 3줄, PET 대기문 및 7개 메뉴 확인창,
저장·덮어쓰기·파일 기반 콜드 부팅 이어하기를 확인했다(`exe45_save_ko_runtime.json`).
같은 문구의 개별 분기, 동적 이름 삽입과 저장 오류·재시도 경로는 아직 실행 분모를 닫지 않았다.
다른 렌더러와 카탈로그 밖 문자열도 남아 있으므로 완전 한글화나 배포 가능 빌드로
주장할 수 없다. 저장 단계 상세는 `SAVE_PROGRESS.md`, 최신 누적 구현은
`LIBRARY_PROGRESS.md`에 기록한다.

후속 고정폭 조사에서 제목 생성은 RAM→VRAM 복사, 칩 이름은 미리 적재한
160레코드 창을 BG 타일맵으로 선택하는 별도 경로임을 확인했다. 8×16 셀에 후보
한글 11,172자가 정적으로 들어가며 두 음절의 실제 표시와 탭/재진입을 확인했지만,
이 실험은 사용 중인 일본어 네 슬롯을 임시로 치환한 것이다. 정식 인코딩이 아니며
기본 개발본에 적용하지 않는다. `FIXEDCELL_PROGRESS.md`는 이 실험의 역사적 기록이다.

2026-09-25에는 사용 중인 일본어 슬롯을 보존하면서 도감 제목 4개를 F9 FC와 별도
한글 뱅크로 실제 번역했다. 누적 69개 단위 개발본에서 첫 진입·네 탭 왕복·재진입,
BIOS 압축 해제와 전체 EWRAM 변경 범위, ROM→RAM→VRAM→화면을 확인했다.
일반 대사와 저장·파일 기반 이어하기도 새 ROM에서 회귀 검사했다. 정본 근거는
`exe45_library_ko_runtime.json`; 칩 이름·mono 설명과 그 밖의 렌더러는 여전히 남았다.

같은 날 후속 칩 이름 조사에서 두 공유 풀의 물리적 스크립트 393개, 포인터 9쌍과
7행×8셀 타일맵 경로를 검증했다. 도감에서 사용하지 않는 것처럼 보인 VRAM도
초기화 프레임과 이름 입력 화면에서 사용되므로 전역 빈 공간으로 채택하지 않는다.
조사 당시 별도 56셀 캐시와 도감 전용 이름 공급 경로는 설계 후보였다.
조사 근거는 `exe45_chip_library_survey_v2.json`에 보존했다.

2026-09-28 최신 선택형 개발본은 `--chip-library`로 세 이름을 추가한 72단위다.
공유 원본 풀·포인터를 보존하는 사설 도감 경로와 56셀 작업 캐시를 구현했다.
정상 입력의 표시·스크롤·지우기·탭 왕복·이름 입력 후 재진입 및 저장/새 실행을
확인했다. 11,172자 공급은 정적/합성 근거이며 실게임 최대 부하 검증과 구분한다.
최대 부하·조건부 아이콘·내용 있는 P.A·다른 소비자는 아직 미검증이다.
현재 정본은 `CHIP_LIBRARY_PROGRESS.md`, `exe45_chip_library_ko_runtime.json`이다.
