# PET 확인 대사 확장 기록 (2026-09-24)

> 아래의 현재 산출물·남은 작업은 PET 단계 당시 기준이다.

## 현재 산출물

- 실행용 개발 ROM: `poc/output/exe45_ko_development_pet_v2.gba`
- SHA-256: `c2c64a0d48dee4f1cd49b906db2068a89f7f041f70688919fe1704ce675268b1`
- 크기: 9,552,232바이트. 동일 입력 재빌드 `_repro.gba`와 해시가 같다.
- 원본 SHA-256 `588a77da006fb0dca0c8addbcc316d7bd4b1c3a42db24750bcfe17b170ac5ef8` 유지.
- 누적 49개 번역 단위: 소개·재회 4개 + PET 대사/선택지 45개.
- 변경하지 않은 730개 카탈로그 아카이브와 포인터는 그대로다.
- 문구는 검토 전 초안이다. 배포 패치 또는 전체 한글판이 아니다.

EXE3 조사에서 가져온 것은 원본 해시 고정·무변경 왕복·주소 독립 확인·허용 쓰기
범위 검증 원칙이다. EXE3의 폰트 주소나 훅을 4.5에 그대로 사용하지 않았다.

`tools/specs/exe45_dialogue_archives_v1.json`이 허용하는 두 일반 대사 아카이브만

공유 문구에 연결된다. 원문·제어 명령·인수·분기 순서·개행 수·앞뒤 빈 줄·선택지
패딩을 보존하고 원본/한글 의미/한글 바이너리 왕복을 모두 검사한다.

PET 최장 정적 줄 전진량은 123픽셀, 선택지 행은 104픽셀이다. 소개 포함 최장은
134픽셀이며 현재 정책의 144픽셀 이하다. 동적 닉네임 앞의 `참,`은 24픽셀로
원문 접두부 33픽셀보다 짧지만, 이것만으로 동적 문자열 런타임 검증을 대신하지 않는다.

### 추가로 해결한 두 직렬화 문제

1. `printPlayerNickname` 뒤의 줄바꿈으로 시작하는 한글 삼중 따옴표 리터럴에서
   TextPet이 첫 E8을 누락했다. 의미 역추출 검사로 검출했고, 선행 개행이 있는
   리터럴만 명시적인 `\n` escape로 직렬화해 원본 개행 경계를 보존했다.
   실패한 `work-pet-v1`은 진단 자료로 남겼으며 실행용 v1 ROM은 만들지 않았다.
2. 원본 문자표에는 ASCII 쉼표가 없어 음절 뒤 확장 인덱스 11172를 추가했다.
   인코딩은 `F9 FC A4 2B`, 폰트 레코드는 11614다. Galmuri 쉼표의 하단 획을
   잘라내지 않도록 1픽셀 위로 옮겨 잉크 2픽셀과 그림자 2픽셀을 보존했다.
   이 글리프는 선택 번역문에서 요구할 때만 추가한다. 소개 단독 회귀 빌드는
   이전 소개본과 같은 `a1b30786...` 해시로 유지됐다.

## 실제 실행으로 확인한 범위

`analysis/exe45_pet_ko_runtime.json`은 고정 해시의 45장 검토 캡처, 12개 결과 파일,
입력 이력, 같은 ROM 체크포인트 연결, 폰트 읽기 기록을 검증해 묶는다.
관찰 문구/캡처 원장은 `analysis/pet_runtime_observations_v2.json`이다.

| 경로 | 관찰 |
|---|---|
| 첫 소개→다음 페이지 | 한글 3줄 표시, A 진행, 다음 일본어 페이지에서 한글 지움 |
| PET 대기 | `자, 뭘 할까?` 표시 및 쉼표 글리프 소비 |
| 토너먼트 | 확인창, 아니요 복귀, 재진입·B 취소, 예→미등록 안내 |
| 플러그인 | 확인창, 아니요 복귀, 예→인터넷 필드 |
| 장비 | 확인창, 아니요 복귀, 예→장비 화면, B 복귀 |
| 라이브러리 | 확인창, 아니요 복귀, 예→칩 목록, B→PET 후속 안내 |
| 메일 | 확인창, 아니요 복귀, 예→메일 종류 화면, B→PET 후속 안내 |
| 통신 | 확인창, 아니요 복귀, 예→통신 종류 화면, B→PET 후속 안내 |
| 저장 | 확인창, 아니요 복귀, 예→원본 저장 확인 화면, B 취소 |

PET 문구 13종 중 10종을 화면에서 관찰했다. 동일 문구가 있는 진입/재진입 스크립트
각각을 특정한 것은 아니므로 45개 단위 전부 런타임 검증 완료라고 하지 않는다.
소개와 PET에서 관찰한 확장 글리프 66종(한글 65종+쉼표)의 레코드 읽기를 확인했다.
보고된 IWRAM 읽기 PC는 `0x03006B32`, `0x03006B34`다.

### 테스트 상태 복원 직후 입력 누락

`pet-ko-v2-prompts` 첫 오른쪽 입력은 실패했고 다음 A가 예를 선택했다. 같은 조건을
원본의 `pet-source-first-input`에서도 재현했다. 원본/패치 양쪽의 캡처를 보존했다.
중립 61프레임 뒤 입력하는 `pet-ko-v2-prompts-settled`에서는 7개 메뉴의 오른쪽→
아니요→대기 복귀가 모두 관찰됐다. 게임 훅 수정 없이 캡처 도우미에 중립 구간을
추가했다. 초기 실패 경로를 성공 경로로 계산하지 않는다.

## 재현

프로젝트 폴더에서 실행한다. 아래 이름이 이미 있으면 새 이름을 지정한다.
기존 빌드·보고서를 덮어쓰거나 작업 폴더를 자동 정리하지 않는다.

```powershell
python -X utf8 -m unittest tools/test_text_catalog.py tools/test_korean_codec.py tools/test_tpl_literals.py tools/test_development_font.py
python -X utf8 tools/verify_korean_roundtrip.py --extra-characters ',' --work poc/visibility/work-codec-new --report analysis/exe45_codec_new.json
python -X utf8 tools/build_development_patch.py --work poc/visibility/work-pet-new --out poc/output/exe45_ko_pet_new.gba
python -X utf8 tools/capture_pet_menu_qa.py --mode prompts --out poc/runtime/pet-prompts-new --mesen 'C:\Users\<user>\AppData\Local\emucap\mesen2\47801\portable\Mesen.exe'
python -X utf8 tools/report_pet_runtime.py --out analysis/exe45_pet_ko_runtime_recheck.json
```

캡처 도우미의 기본 manifest와 origin은 검토된 v2 및 `pet-ko-v2-cold`다.
새 ROM 해시의 런타임에 기존 체크포인트/관찰을 재사용하면 안 된다. 먼저 새 ROM을
콜드 부팅하고 같은 일반 입력을 거친 뒤 `--manifest`, `--origin`을 명시한다.
새 캡처는 직접 검토 후 별도 관찰 원장을 만들어야 하며 완료 플래그만으로 통과하지 않는다.

단위 테스트 18개 통과. 코덱 v3는 한글 11,172자+쉼표의 연속/스크립트 시작/
keyWait 직후 및 원본 732개, 1,065,382바이트 페이로드 왕복을 통과했다.
