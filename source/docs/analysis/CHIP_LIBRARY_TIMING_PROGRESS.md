## 시험 조건

원본 코드·ROM 글꼴·실제 GBA BIOS 복사기를 그대로 실행하면서 CPU 읽기 결과만
별도 도구로 대체했다. 선택기의 7행에는 알려진 칩 ID 1, 각 행에는 8개 한글,
조건부 아이콘에는 표시 유무 1을 공급했다. 한글 번호 0..54와 11171을 사용했다.
이는 원본 ROM/RAM 쓰기나 진행도 변경은 아니지만 **획득·선택 전제를 우회한 시험**이다.
실제 이름/번역이 아니며 제품 빌드에 들어가지 않는다. 메가/기가 탭에 캐논 시험 ID를
공급한 것은 타일·복사 경로 시험이지 해당 칩의 정상 분류를 뜻하지 않는다.

시작점은 세 경로 모두 `chip-ko-v1-input-lifetime`의 같은-ROM PET 체크포인트다.
도구·환경·정확한 패드 입력과 산출물은 각 실행 `result.json` 및 환경 파일에 묶였다.
시험 체크포인트는 `diagnostic_checkpoint.mss`로 따로 보존해 정상 실행의 시작점으로
사용할 수 없게 했다. 픽셀은 가공하지 않은 에뮬레이터 캡처에서 검사했다.

격리 시험의 926회 이름 갱신·6,482행에서 매번 56개 글리프 복사와 7개 아이콘 복사를
확인했다. 실제 선택된 글리프 원본 주소가 각 행/열의 시험 번호와 일치하며,

한글 캐시 `8040..8E3F`와 겹치지 않는다. 이 시험에서 별도 아이콘 복사 경로가
실제로 실행됐다는 것이 이전 정적 주소 조사보다 추가된 근거다.

## 열린 성능 문제

같은 첫 진입 입력으로 정상 경로는 이름 갱신 194회/간격 1프레임 193회를 보였다.
56셀+7아이콘 경로는 193회/간격 1프레임 191회 및 2프레임 1회를 보였다.
두 번째 갱신 다음의 첫 진입 구간에서 추가 간격이 생겼고, 이후 안정 구간 전체가
30fps로 떨어진 것은 아니다. 소요 시간의 정확한 분포와 주사선은 보고서에 있다.
정상 이름 갱신 약 9,900클록에 비해 최대 부하 갱신은 약 48,400클록이었다.

최대 부하에서는 화면 표시 중인 주사선에도 글리프를 복사한다. 현재 시험 문자열은
고정돼 있으므로 안정 스크린샷이 맞는다는 사실만으로 동적으로 이름이 바뀔 때의
순간 깨짐이 없다고 증명할 수 없다. 실기/오디오 동기화도 아직 검사하지 않았다.

불필요한 매 프레임 복사가 원인 후보지만, 아이콘 부하와 분리한 단일 요인 비교는
남았다. 다음 작업은 **56셀/아이콘 유무를 분리한 비교 → 갱신 필요 여부·전송 시점의
개선안 평가 → 같은 조건과 기존 정상 경로 회귀 검증**이다. 어휘를 줄여 부하를
숨기거나 이 성능 문제를 해결된 것으로 처리하지 않는다.

## 실패한 시험과 저장 파일 부수 효과

- `stress56-icons`, `stress56-icons-diagnostic`은 실패한 시험 입력이다. Lua `/`가
  만든 실수의 나머지 값을 반환해 하위 바이트가 적용되지 않았다. Mesen은 정수
  반환값만 대체한다. 실제 복사 원본 주소가 예상 글리프와 다른 것으로 원인을
  분리했고 `math.floor`로 정수화한 뒤 새 경로에서 56개 번호를 전부 확인했다.
  실패한 결과는 보존하고 성공 통계에서 제외했다.
- 시험 전 읽기 전용 `timing-native` 실행 뒤 **격리 테스트용** `.sav`가
  `99bb…b470`에서 `7118…9063`으로 돌아갔다. 오래된 체크포인트 실행 뒤 관찰된
  부수 효과이며, 읽기 전용 관찰이 디스크 저장 보존까지 보장하지 않음을 확인했다.
  이후 두 성공 격리 시험 자체에서는 `.sav` 변화가 없었다.
- 검증 완료 저장 사본으로 `99bb…b470`을 복원했고, 복원 전 `7118…9063`도 별도
  디렉터리에 보존했다. 대상·원본·복원 해시와 재발 방지는
  `chip_timing_save_restoration_v1.json`에 기록했다. 사용자 에뮬레이터 저장 파일과
  이전 save-v1 검증용 두 저장 파일은 대상이 아니다.
- 이전 진행 문서의 “설명 렌더링이 행 버퍼를 재사용”이라는 원인 표현은 과도했다.
  확인된 사실은 프레임 끝의 앞쪽 RAM 내용이 파서 반환 당시와 다르다는 점이다.
  후속 UI의 임시 버퍼 사용으로 해석하지만 정확한 마지막 쓰기 경로는 별도 실행
  추적 전까지 확정하지 않는다. 원래 타일/픽셀 검증 결과에는 영향이 없다.

확보하고 56셀/아이콘 진단 관찰기를 LDM 경계에 맞춰, 같은 의미 상태에서
갱신 간격과 clock을 비교하는 것이다. CHIP-CACHE-TIMING-001은 OPEN이다.

## 워드 복사 최악 부하 시간 비교: 개선 확인, 초기 지연 미해결

`capture_chip_wordcopy_matrix.py`는 고정 matrix 관찰기의 복사 진입점을
첫 LDM으로 바꾸고 BIOS 전용 r2 길이 조건만 제거한다. 실제 64바이트 비교,
56셀/7행/7아이콘과 디스크립터 불변 검사는 유지한다. 모든 진단 체크포인트는
격리하며 정상 플레이로 재사용하지 않는다. ROM/번역은 이번에 바꾸지 않았다.

기존 ROM과 후보 각각의 cold 체크포인트에서 동일 8개 입력으로 진입했다.
두 cold 상태는 frame 7473/scanline 160과 의미상 PET 상태가 같지만 CPU PC,
PPU cycle(1 대 6), EWRAM은 동일하지 않다. 따라서 완전히 같은 기계 상태의
A/B 비교라고 주장하지 않는다. 후보 56셀과 0셀 대조는 **동일 체크포인트**다.

| 조건 | 이름 그룹 중앙값 clock | 전체 갱신 중앙값 clock | 복사 중앙값 clock | 2프레임 간격 |
|---|---:|---:|---:|---|
| 기존 BIOS, 56셀·7아이콘 | 48,418 | 66,249 | 659 | 두 번째 그룹 뒤 1회 |
| 후보 워드, 56셀·7아이콘 | 20,587 | 38,425 | 183 | 두 번째 그룹 뒤 1회 |
| 후보, 원래 숫자 56칸·7아이콘 | 6,772 | 24,585 | 복사 없음 | 없음 |

56셀 두 실행은 각각 313그룹, 글리프 17,528복사, 아이콘 2,191복사다.
0셀 대조는 314그룹이며 313개 연속 간격이 모두 1프레임이다.
이름 처리 중앙값은 57.48%, 전체 갱신은 42.00% 감소했지만 초기 지연은 남았다.
따라서 “BIOS 호출 교체만으로 지연 해결” 가설은 기각한다. 후보 내부의
동일 상태 대조는 잔여 한글 처리 부하와 초기 지연의 연관성을 유지한다.
고정 글리프 반복 시험이므로 이름이 바뀌는 순간의 tearing 부재는 증명하지 않는다.

자료: `chip-legacy-matrix-cold56`, `chip-wordcopy-matrix-cold56`,
`chip-wordcopy-matrix-cold0` (모두 poc/runtime 아래).
재검증: `python -X utf8 tools/report_chip_wordcopy_timing.py`.
해시·작업량·시작 상태·초기 그룹 시간은
`analysis/exe45_chip_wordcopy_timing_v1.json`에 기록했다. 검사기 8개 통과.
기존 검증 저장 99bb…b470 보존을 다시 확인했다.

스킬의 반복 전송/원인 제거 사례에 따라 전송량 감소를 FPS나 원인 해결과
동일시하지 않았다. CHIP-CACHE-TIMING-001은 OPEN, 후보는 채택 전이다.
다음 구별 관찰은 후보 56셀/0셀의 두 번째 그룹 시작부터 세 번째 그룹까지
전체 프레임 대기·인터럽트·표시 갱신 순서를 추적하는 것이다. 이미 줄어든
복사 루틴만 추가 최적화하기 전에 지연이 처음 생기는 대기 경계를 확인한다.

## 초기 지연의 대기 경계 관찰

동일 후보 403fc…/동일 cold 상태에서 `chip-wordcopy-wait0`와
`chip-wordcopy-wait56`을 실행했다. 처음 4개 이름 그룹 주변의 메인 루프
경계만 기록했다. ROM과 원본 메인 루프 바이트는 변경하지 않았다.

두 번째 갱신 뒤 08000374 함수는 DISPSTAT bit 0이 꺼질 때까지 기다린다.
이후 08000344가 다음 VBlank를 기다린다. 해당 PC의 리터럴을 별도 계산해
두 함수의 DISPSTAT 주소가 04000004임을 확인했다.

| 조건 | 08000374 진입 | 현재 VBlank 종료 대기 | 다음 VBlank 대기 | 재개 |
|---|---|---:|---:|---|
| 원래 숫자 56칸 | frame 7954, line 154 | 21 clocks | 7,339 clocks | frame 7955, line 160 |
| 한글 56칸 | frame 7955, line 165 | 75,842 clocks | 198,662 clocks | frame 7956, line 160 |

한글 조건은 추가 처리로 다음 대기 진입이 VBlank 경계를 넘는다. 원래 루프가
진행 중인 VBlank를 먼저 끝까지 기다린 후 다음 VBlank를 기다리는 것이
이번 실행에서 한 프레임 간격이 추가되는 경로다. 전체 이름 그룹 안의
복사 자체가 두 프레임을 차지한 것으로 해석하면 안 된다.

제한/정정: 기존 시간 시험과 모든 clock이 같지는 않다. 0셀은 두 번째 그룹에서
315 clocks, 56셀은 네 번째 그룹에서 304 clocks 차이가 처음 나타난다.
원인은 미확정이며 관찰 무영향/사이클 단위 결정성을 주장하지 않는다.
갱신 수·간격·지연 위치는 재현된다. 초기 관찰기의 counter/threshold라는
필드명은 잘못 붙였다(실제 읽은 주소 0200F9F0/02010210). 이 값은 결론에서
전부 제외하고 도구의 후속 버전은 주소 이름으로 수정했다. 기존 생성 Lua와
결과를 보존했다. 실제 비교 명령의 주소는 02010210/0200F808이다.

재검증 도구: `tools/report_chip_wait_trace.py`.
자료/해시/제외 필드: `analysis/exe45_chip_wait_trace_v1.json`.
CHIP-CACHE-TIMING-001은 OPEN이다. 원래 게임 전체의 VBlank 대기를 바꾸지
않는다. 다음 수정 후보는 정상/변경된 행의 글리프 재공급 필요성을 구분하여
반복 작업을 줄이는 것이며, 캐시 식별자 저장 공간과 무효화 시점의 소비자
근거를 먼저 확보해야 한다. 또는 초기 진입의 작업 배치를 해당 화면에만
한정해 조정할 수 있는지 조사한다. 아직 어느 방식도 채택하지 않았다.

## 캐시 식별자 저장 후보와 재진입 수명 조사

후보 403fc…에서 `chip-wordcopy-cache-ownership`(17입력)과 그 정상 체크포인트의
`chip-wordcopy-cache-reentry`(10입력)를 실행했다. 첫 경로는 스탠더드/메가/기가/
P.A 왕복과 PET 복귀, 둘째 경로는 후속 대화 및 도감 재진입이다. 마지막 재진입
화면의 캐논·에어슛·발칸1을 직접 확인했고 두 경로 모두 도감 로더 호출이 있다.

새 관찰기는 RAM/VRAM에 쓰지 않는다. 아직 캐시 태그 구현이나 할당은 없다.
실험 대상 태그 후보는 `06008E40..06008EAF`의 112바이트(56×uint16)다.

- 총 874개 프레임의 활성 mode-0 4bpp BG 맵에서 태그 후보 타일 참조 0건.
- `06008000..06008FFF` 쓰기 콜백 37,296건은 실제 검증된 워드 글리프 복사
  2,331회×16개의 32비트 쓰기와 일치한다. 8개 STM 명령(콜백 r15=PC+4) 외
  쓰기 지점은 없으며 각 명령의 쓰기 분포도 일치한다.
- BG 맵 쓰기 양성 대조 1,744,896건. 진입/재진입 로더의 허용 외 EWRAM 변경 0.
- 원본 도감 초기 자산 23개를 다시 해제/계산해 태그 후보와 겹치지 않음을 확인.
- 도감 초기화 함수 `08042778`의 마지막 해제 호출 `080427A0..080427A7`,
  복귀 `080427A8`을 조사했다. 재진입마다 초기화를 수행할 후크 후보이며
  아직 덮어쓰지 않았다. 후크 구현 시 원래 두 리터럴 로드와 BL 효과를 보존해야 한다.

한계: 태그 영역만의 별도 쓰기 감시는 아니며, 검증된 글리프 쓰기 지점·횟수로
전체 창의 쓰기를 설명했다. 프레임 끝 맵 관찰은 순간적 중간 프레임 참조를
배제하지 않는다. 다른 화면(이름 입력)이 이 VRAM을 재사용한다는 기존 증거는
여전히 유효하므로 전역 빈 공간 또는 모든 경로의 안전으로 일반화하지 않는다.

자료: `analysis/exe45_chip_cache_ownership_v1.json`.
재검증: `python -X utf8 tools/report_chip_cache_ownership.py`.
기존 세이브 99bb…b470 보존 확인. 기존 개발본과 후보 ROM 모두 변경하지 않았다.

다음 실험 설계: 글리프 인덱스+1을 태그로 저장(0=무효), 64바이트 복사를
완료한 뒤 태그를 게시하며 모든 도감 진입에서 태그를 초기화한다. 일치한 셀만
재복사를 생략하고 기존 타일맵/패딩 처리는 유지한다. 이 설계의 새 실험 빌드에서
최초 복사·동일 글자 재사용·글자 변경·태그 경계·탭·재진입·다른 화면 덮어쓰기
이후 무효화 및 56셀 시간 시험을 검증해야 한다. 채택과 문제 해결은 아직 미완료다.

## 태그 캐시 실험 구현 및 초기화 훅 실패 교정

`--chip-library --chip-word-copy --chip-cache`를 명시해야 캐시를 포함한다.
기존 기본/워드 복사 경로는 유지된다. 워드 전용 재빌드는 기존 403fc…와 같다.
태그는 06008E40의 56개 uint16이며, ROM 한글 번호+1을 저장한다. 적중 시
복사를 생략하되 행 맵과 패딩 처리는 수행한다. 누락/변경 시 64바이트 복사가
끝난 뒤 태그를 쓴다. 080427A0의 원래 리터럴 2개 로드와 LZ 호출을 재현하고,
그 뒤 모든 태그를 0으로 초기화한 다음 080427A8로 복귀한다.
원래 압축 데이터 포인터 저장 위치를 읽으므로 값의 소유권은 기존 빌드에 남는다.

첫 후보 `chip_cache_v1.gba` (SHA 531bbf7e…89f059b)는 도감 진입 시 검은 화면이
발생해 **기각**했다. 초기화 래퍼의 `mov lr,pc`가 짝수 복귀 주소를 만들었고,
원래 LZ 래퍼의 `bx lr`가 ARM 상태로 전환했다. 기존 합성 검사에서 LZ 대체가
LR에 강제로 1을 더해 이 결함을 숨겼다. 실패 ROM과 runtime/chip-cache-v1-tabs는
보존했다. 해당 결과는 complete=false, 캐시 양성 관찰은 0이며 성공 통계에서 제외한다.

보강한 CPU 검사는 SWI 작업만 대체하고 원래 `080EC15A: bx lr`를 실제 실행한다.
이 검사는 v1을 Invalid instruction으로 거부한다. v2는 최종 배치에서 계산한
홀수 복귀 주소를 명시하고 그 대상이 실제 pop {r7} 경계임을 빌드에서 검사한다.
원래 LZ 결과의 r0..r3, 보존 레지스터와 스택, 최종 LR를 유지한다.

- 현재 캐시 실험 후보: `poc/output/exe45_ko_development_chip_cache_v2.gba`
- SHA256: `038ac069ff83dc920e82a9f9663f43fc0d7a973d1f75d39b4d7e33c6f1dffae7`
- `_repro.gba`와 바이트 동일.
- `analysis/exe45_chip_cache_cpu_v2.json`: 34,054벡터, 22,855복사.
  11,172자 각각 cold/hit/change 및 기존 행·가드 검사를 실행한다.
  3가지 초기 VRAM 패턴에서 초기화가 112바이트만 지우는지와 원래 LZ 인자,
  복귀 모드, 레지스터 보존을 검사했다. LZ 해제 본체는 대체하므로 실제 GBA
  해제/화면 동작 증거가 아니며, 정상 실행 및 시간 검증이 별도로 필요하다.

캐시 후보는 기본 개발본으로 채택하지 않았다. CHIP-CACHE-TIMING-001은 OPEN이다.

### v2 실제 실행 결과: 고정 최악 부하의 초기 지연 재현 해소

v2의 별도 콜드 부팅에서 만든 상태로 `chip-cache-v2-tabs`를 실행했다.
정상 입력 14개에서 도감 진입/네 탭 왕복/PET 복귀를 수행했다. 태그 초기화
1회, 한글 셀 검사 1,820회 중 실제 복사 7회·캐시 적중 1,813회를 확인했다.
매 적중/누락마다 태그 값과 실제 VRAM 64바이트를 ROM 글리프와 비교한다.
표준 탭 7/13 화면에서 캐논·에어슛·발칸1의 타일/패딩/픽셀 마스크도 일치했다.

`chip-cache-v2-matrix56`은 동일 후보 cold 상태에서 별도로 시작한 **진단 읽기
대체** 시험이다. 56한글 셀·7아이콘의 고정 입력이며 정상 취득 증거가 아니다.

- 314개 그룹/2,198행을 검사, 313개 갱신 간격이 모두 1프레임.
- 글리프 복사는 최초 56회만 발생하고 나머지 그룹은 모두 0회. 각 행의 실제
  글리프 바이트는 적중 여부와 관계없이 검증했다. 아이콘 복사 2,198회.
- 이름 그룹 중앙값 10,184 clocks, 전체 갱신 중앙값 27,996 clocks.
- 첫 그룹은 cold miss로 21,444 clocks. 후속 그룹의 초기 2프레임 간격이
  이번 재현에서는 발생하지 않았다. 기존 워드 전용 20,587/38,425 clocks와
  구분하며, 서로 다른 ROM의 모든 기계 상태가 동일하다고 주장하지 않는다.
- 원래 프레임 대기 코드는 변경하지 않았다. 글리프/번역 범위를 줄이지 않았다.

재검증: `python -X utf8 tools/report_chip_cache_runtime.py`.
결과: `analysis/exe45_chip_cache_runtime_v2.json` (정상/진단 결과 해시 별도).
최종 Thumb 복귀 경계 검사 추가 후 빌드한 `_guarded.gba`도 v2와 같다.
기존 49개 검사 통과; 원본과 기존 검증 세이브 보존.

고정 부하 재현만 통과한 상태다. 스크롤/다른 글자/긴→짧은 이름, 다른 화면이
VRAM을 덮은 뒤 도감 재진입, 저장/재부팅, 조건부 아이콘과 변화하는 이름의
표시 수명 회귀가 남았다. 따라서 전체 이슈는 아직 OPEN이며 기본 개발본은
기존 ce839…를 유지한다. 다음 작업은 **v2 정상 스크롤·재진입 회귀**다.

콜드 diagnostic 체크포인트 실행은 해당 후보의 **격리된 시험용 SRAM**을
이전 상태로 돌렸다. 새 세이브 증거는 각 단계의 독립 snapshot에 보존되어 있다.
`saved-checkpoint-return`은 검증된 같은 ROM의 reboot 체크포인트를 정상
실행하여 새 SRAM 6de509d7…로 시험 폴더를 되돌렸다. RAM/파일을 수동
편집하지 않았다. v2 보고서는 현재 시험 세이브까지 해시를 대조한다.
사용자 원본 ROM 및 chip-survey 기준 세이브는 각각 588a77da… / 99bb577d…로 유지됐다.

현재 판단: CHIP-CACHE-TIMING-001의 재현된 초기 한 프레임 손실은
**표준 도감의 지정된 muted-Mesen 부하와 회귀 경로에서 수정 검증됨**.
실기·청취·전체 플레이 검증 또는 배포 완료로 확대하지 않는다.
기존 기본 개발본은 보존하고 late-wait 옵션은 명시적으로만 선택한다.
